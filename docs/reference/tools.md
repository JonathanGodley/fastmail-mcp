# Tool reference

## Available Tools (41 Total)

### Email Tools

> **Draft-first compose:** `draft_email` saves a draft in every mode, and **`send_draft` is the only tool that transmits a composed message**. To compose and send: `draft_email` → `send_draft`. Gating `send_draft` does **not** gate all outbound mail: see [Calendar invitations send mail](calendar.md#calendar-invitations-send-mail).
>
> **Recipient format:** every recipient field (`to`/`cc`/`bcc`/`replyTo` on `draft_email` and `edit_draft`) accepts each entry as either a bare address (`a@x.example`) or the RFC 5322 `"Name <email>"` form (`Alice <a@x.example>`), which is parsed into a display name + address. The SMTP envelope always uses the bare address. All four **fail closed**: a whole value that cannot be read as a list is refused naming the parameter, and a non-string or blank entry is refused by index, rather than either being dropped and read as a field you never passed (see [Parameter validation](responses.md#parameter-validation), which also covers what an empty value means on each tool).
>
> **Draft sender name:** drafts written by `draft_email`/`edit_draft` carry a display name alongside the From address. To state it yourself, pass `from` as `"Name <email>"` on either tool ([#161](https://github.com/JonathanGodley/fastmail-mcp/issues/161)): the address half is matched against your verified identities as a bare address is, and the name half is written through unvalidated. A name you pass wins outright. Otherwise a compose writes the matched identity's name, and an edit keeps the name the stored draft already carries for the address it writes, falling back to the identity's name only for a draft that carries none, so an edit that does not touch `from` never reverts a name you set ([#152](https://github.com/JonathanGodley/fastmail-mcp/issues/152)). A stored `from` matching no verified identity (an address removed from the account, or a draft made elsewhere) keeps both its own address and its own display name (blank/whitespace-only counts as no name). See [`docs/email-bodies.md`](../email-bodies.md).
>
> **Wildcard identities are not addresses:** a Fastmail account can hold a *wildcard* identity, whose address is the pattern `*@example.com` rather than a real address. It verifies, and signs, any concrete address in that domain — but the pattern itself must never reach a From header, so **a pattern is refused wherever it would be used as an address** ([#160](https://github.com/JonathanGodley/fastmail-mcp/issues/160)). That covers all three directions the pattern can arrive from. **Passed as a `from` value** — `draft_email` or `edit_draft` with `from: "*@example.com"`, or the same pattern inside the `"Name <email>"` form — it is refused before anything is written, naming the address half. **Selected as the identity's own address** — `draft_email` with no `from` while the account default is a wildcard, or `edit_draft` with no `from` on a draft that carries none either — it is refused with a different message, since there the fix is to pass a `from` at all. And **already stored on a draft**, `send_draft` refuses to transmit it, which covers a draft written by another client. **Everything else composes normally.** Passing a concrete `from` in that domain works, is verified by the wildcard identity and carries its signature; and a draft that already stores a concrete From edits normally, even when that address matches no identity at all.

- **list_mailboxes**: Get the mailboxes in your account. Each one carries its `path` - the root-anchored, `/`-separated location - which you can paste straight back into any mailbox parameter. Pass `parent` to list one folder's direct children instead of the whole account.
  - Parameters: `parent` (optional - id, role, name, or path; lists that mailbox's direct children only; a blank value is rejected - omit it to list every mailbox), `verbose` (optional, include all fields), `raw` (optional, return original JMAP response - untransformed JMAP carries no `path`)
- **create_mailbox**: Create a mailbox (a Fastmail folder, which is also what a label is). Returns the new mailbox in the same shape `list_mailboxes` returns, `path` included, so you can use it as a move destination or a label straight away without a second lookup. `name` is a leaf name and must not contain `/`; to nest the mailbox, pass `parent` (which itself accepts an id, role, name, or path).
  - Parameters: `name` (required - leaf name, no `/`), `parent` (optional - id, role, name, or path; omit to create at the top level), `verbose` (optional, include all fields), `raw` (optional, return original JMAP object)
- **list_emails**: List recent emails across all mailboxes (or one, via `mailbox`). **Trash and Spam are excluded by default** (set `includeTrash`/`includeSpam` to include them); drafts are included (set `excludeDrafts` to omit them). When a Trash/Spam match is withheld, a trailing note reports how many — so no note means nothing filed only in Trash/Spam matched, and you need not re-search to check. This is not an arrivals feed: "all mailboxes" means every folder except Trash and Spam, so Sent copies, drafts and custom folders come back alongside newly received mail — pass `mailbox: "inbox"` for delivered mail only. One mailbox is all this tool scopes to; to intersect several mailboxes or exclude some, use `search_emails` with no query (see [Scoping across several mailboxes](email.md#scoping-across-several-mailboxes)). Pass a small `limit` (e.g. 10) for a quick check of what has come in.
  - Parameters: `mailbox` (optional — [id, role, name, or path](email.md#naming-a-mailbox); scoping to a mailbox ignores the default exclusion; a blank value is rejected rather than read as every mailbox - omit it instead), `limit` (default: 20, max: 100), `position` (optional offset — see [Result counts and paging](responses.md#result-counts-and-paging-position)), `ascending` (optional, oldest first), `excludeDrafts` (optional), `includeTrash` (optional), `includeSpam` (optional), `fields` (optional array — return only these fields; `sentAt` is returned only when named here, e.g. `fields: ["id","date","sentAt"]`, see [Field projection](responses.md#field-projection-fields)), `raw` (optional, return original JMAP response)
- **get_email**: Get a specific email by ID. Returns plain text body with HTML omitted (bodyHtmlSize hint provided). Only use `verbose` if you specifically need the HTML body — it can be very large for marketing emails. To read a large HTML body without the rest of the message alongside it, use `fields: ["bodyHtml"]`.
  - Parameters: `emailId` (required), `verbose` (optional, include HTML body — can be 50K+ chars for rich emails), `fields` (optional array — return only these fields, see [Field projection](responses.md#field-projection-fields)), `stripQuoted` (optional, drop quoted reply history from `bodyText`), `raw` (optional, return original JMAP response)
  - `stripQuoted` is opt-in and reports what it did — see [Reading long threads cheaply](email.md#reading-long-threads-cheaply).
- **draft_email**: Compose a draft in one of three modes — `new`, `reply` or `forward` — placing this server's generated blocks yourself with **body tokens**. Three tokens are recognised in `textBody`/`htmlBody`: `{{signature}}` (the sending identity's configured signature), `{{quote}}` (the quoted original, `reply` only) and `{{forward}}` (the forwarded-message block, `forward` only). **Nothing is added for you** — a body with no `{{signature}}` is stored unsigned and, when the sending identity has a signature, the result says so (unless the body is blank or shows nothing, where there is nothing to sign), and a reply with no `{{quote}}` is stored without the conversation. Each mode accepts exactly its own history token and refuses the other; a near-miss spelling (`{{Quote}}`, `{{{quote}}}`) is refused rather than shipped as braces, while whitespace inside the braces is trimmed, so `{{ quote }}` is the token and a single brace each side (`{quote}`) is ordinary prose. The same token twice in one part is refused as well — expanding it twice would store the block twice. Tokens are expanded **once, at write**, so the stored draft is the finished message: `get_email` and the Fastmail web app both show what will be sent, and a body read back carries no token to re-expand. A block is substituted at the token's exact position with nothing added around it, so the spacing at the join is yours — the canonical shape is the sign-off above the history with one blank line (text) or one empty block element (HTML) between them. **`{{signature}}` is the whole sign-off**, closing line included, so write no "Regards" of your own above it unless `list_identities` shows a signature with no closing line. **The result shows each join** (see [Signing a message](email.md#signing-a-message)). A token in one supplied part but not in the other supplied part is refused, where a blank or whitespace-only part counts as not supplied; supply one part only (an `htmlBody` supplied alone gets a text alternative derived from it whenever the HTML yields text; a `textBody` alone ships no HTML), or place the token in both. A body that expands to nothing visible is refused rather than stored. To write the braces literally, escape them with a backslash (`\{{signature}}`, which in JSON is `"\\{{signature}}"`); the backslash is consumed only before one of the three names. **A `reply` is reply-all by default** ([#184](https://github.com/JonathanGodley/fastmail-mcp/issues/184)): pass neither `to` nor `cc` and `to` becomes the original's `Reply-To` (falling back to its `From`) while `cc` carries everyone else the original's To and CC named — minus your own verified identities (wildcard identities included), minus whoever `to` already covers, deduplicated by address and omitted when nothing is left. **The original's own `Bcc` list is carried the same way** ([#189](https://github.com/JonathanGodley/fastmail-mcp/issues/189)): whole, in the original's order, display names kept, deduplicated by address — and with nothing dropped for being one of your identities or for already appearing in the reply's `to` or `cc`. The carry keys on the original carrying a `Bcc` header and on nothing else — there is no provenance check. Mail you received normally carries none, so a reply to it usually carries nothing; an imported or migrated message that does carry one has its list carried like any other. **Naming either `to` or `cc` turns off the cc and Bcc carry**; an absent `to` still falls back to `Reply-To`/`From`. Naming `bcc` is different: it is additive rather than narrowing, so it replaces the carried Bcc alone and leaves the `to` and `cc` defaults running (an empty `bcc` — `[]` or `""` — is treated as omitted). The result reports the `to`, `cc` and `bcc` actually stored, and says when the Bcc list was carried. **Always saves a draft, never transmits** — review it, then send it with `send_draft`, which on `reply`/`forward` marks exactly the stored copy passed as `originalEmailId` (a forward of an original with no usable Message-ID cannot be marked, and the result says so). Quoted and forwarded HTML is reproduced **sanitised** and re-sent under your From address, and **images the original displayed are carried into the block** on a bound this server does not narrow — a quoted image is only carried when the HTML part is non-blank **and** carries the history token, otherwise the block ships as text and the result says how many images went with it — dropped on a reply, riding as regular attachments on a forward (left out when `includeOriginalAttachments` is false), where the result also says the original ships HTML and that putting `{{forward}}` in `htmlBody` keeps the formatting and the images both. The result carries a **receipt**: which tokens expanded in which part, how many times, in what order they landed, which were removed for having nothing to expand to (and why), any `{{…}}` spelling in your body it left unexpanded (each distinct spelling once, however many times and in however many parts you wrote it), and whether the `asAttachment` filler body (`Forwarded message attached.`) was inserted. **The result also carries `bodyHash`**, read back off the saved draft, so a join can be repaired with `edit_draft` `bodyEdits` without reading the draft first; when one cannot be issued, `bodyHashWithheld` says why, giving the read-side and read-back reasons that `edit_draft`'s result gives. (This tool returns a status string plus the receipt, the join lines and the body hash, not email data, so `raw`/simplification do not apply.)
  - Parameters: `mode` (**required**, one of `new`/`reply`/`forward`, no default), `originalEmailId` (required for `reply`/`forward`, refused on `new`), `to` (required on `forward`; optional on `reply`, where it defaults to the original's `Reply-To` else its `From` — and naming it turns the reply-all carry off; optional array or a single bare string), `cc` (optional; on `reply` it defaults to the reply-all carry above, and naming it also turns that carry off), `bcc` (optional; on `reply` it defaults to the original's own Bcc list carried whole, and naming it replaces that list without touching the `to` and `cc` defaults), `from` (optional — a bare address or the `"Name <email>"` form, where the address half must match a verified identity and the name half is written through unvalidated; omit the name and the matched identity's name is written. Also picks, by that address half, the identity whose signature `{{signature}}` expands to; required when the account's default identity is a [wildcard](#email-tools), and the wildcard *pattern* itself is refused as a value here — pass a concrete address in its domain), `replyTo` (optional), `mailbox` (`new` only — [id, role, name, or path](email.md#naming-a-mailbox); defaults to the Drafts folder, resolved by its `drafts` role, so an account with no such mailbox is refused rather than guessed at by name; **naming anywhere but Drafts makes the draft unsendable until it is moved back** — the draft is filed into that mailbox and that mailbox only, and `send_draft` sends only a draft that is in Drafts, so use this for a draft you are parking, not one you are about to send), `subject` (optional; `reply` inherits `Re: …` and `forward` inherits `Fwd: …`, neither double-prefixing, and a counted or spaced prefix such as `Re[2]:` or `RE :` counts; typing a reply or forward prefix (`Re:`, `Fwd:`, `Fw:`, with or without an `[n]` counter) into a `new` subject draws a note, since `new` writes no threading headers — unless you pass `inReplyTo`/`references` yourself), `textBody` (optional), `htmlBody` (optional — supplying it non-blank and carrying the history token is what lets the block show the original's images), `inReplyTo` (`new` only; array or a single bare string), `references` (`new` only; array or a single bare string), `asAttachment` (`forward` only — refuses `{{forward}}` alongside it, since the original is already carried whole; a forward with **neither** `{{forward}}` nor `asAttachment` is refused. **The `.eml` is the raw stored message**, so it carries its full transport headers (the Received chain, authentication results) and, when forwarding a message from Sent, any Bcc recipients, none of which an inline forward exposes; see [docs/security-model.md](../security-model.md)), `includeOriginalAttachments` (`forward` only, default true; ignored with `asAttachment`), `attachments` (optional).
- **edit_draft**: Edit an existing draft email. Since JMAP emails are immutable, this creates a replacement draft and permanently deletes the old one, as the Fastmail web app does when it saves a draft (so the returned email ID is new). **A draft in Trash is rejected** — an edit would otherwise recreate it in Trash — and the refusal says where it is; move it back to Drafts with `move_email` and edit it again. A draft filed in any other mailbox is edited in place there. The edit preserves the draft's threading headers (In-Reply-To/References), attachments, and other keywords. The replaced draft is **not recoverable** — nothing is left in Trash ([#229](https://github.com/JonathanGodley/fastmail-mcp/issues/229)), so a body you replace is gone; `bodyHash` is what stops an edit made from a stale copy (the draft changed in the web UI or another client in between). A body edit's result gives the saved body sizes, marking a plain-text part this edit derived from the HTML. On the rare failure where the replacement is created but the old copy can't be deleted, you are left with a duplicate draft rather than none, and the result says so; if the old copy was already gone, the result warns that something else replaced or deleted it during the edit. Only fields you provide are changed; omit a field to leave it unchanged. Any edit that writes or clears a body must pass `bodyHash` from a `get_email` read of that draft, or from the `draft_email` or `edit_draft` result that saved it.
  - **Embedded (`cid:`) images survive an edit** ([#13](https://github.com/JonathanGodley/fastmail-mcp/issues/13)). An image the edited body still displays keeps its identifier, so a client that has already rendered the draft doesn't renumber it — hand back the `<img src="cid:...">` references you read and the images stay. An image the body no longer displays comes **off** the draft when this server put it there and becomes a **regular attachment** when it came from elsewhere — those bytes aren't this server's to discard. The result says what the draft ended up embedding, and what came off it. A `cid:` reference to one of this server's own identifiers naming **no part the draft carries** is rejected: passing one back is how images keep displaying, but authoring a new one points at nothing that can ever exist. Two body shapes still can't be rebuilt faithfully and are **rejected**: a body part that is neither text nor a carriable image, audio, video or attached message; and a body that interleaves two parts of the same text type (the Apple Mail text-image-text layout, [#85](https://github.com/JonathanGodley/fastmail-mcp/issues/85)) — recreate those drafts instead. And if the draft's stored body already references an image that isn't attached, editing its **body** is rejected until the edit resolves that — replace the body, or add an `attachments` item supplying the missing `cid`; metadata and attachment edits still work on such a draft.
  - Parameters: `emailId` (required), `to` (optional array), `cc` (optional array), `bcc` (optional array), `from` (optional — a bare address or the `"Name <email>"` form; a name written here **replaces** the draft's stored display name, while a bare address keeps it (switching to a different address you can send as writes that identity's name instead, since the draft carries no name for the new address), and a name can never be *removed*, only replaced. Omitting `from` keeps the draft's own From, including one written under a [wildcard identity](#email-tools); it is required only on a draft that carries no From while the account default is a wildcard, and the wildcard *pattern* itself is refused as a value here — pass a concrete address in its domain), `subject` (optional; writing a reply or forward prefix (`Re:`, `Fwd:`, `Fw:`, with or without an `[n]` counter) onto a draft that carries no threading headers draws a note, since an edit cannot add them), `textBody` (optional), `htmlBody` (optional), `bodyEdits` (optional array of `{find, replace}`: exact edits to the stored body, below), `replyTo` (optional array), `bodyHash` (**required for any edit that writes or clears a body**, below), `expandSignature` (optional boolean, default false — expands a `{{signature}}` you wrote, below), `clearFields` (optional array), `attachments` (optional array — **appends**), `removeAttachments` (optional array of blobId/name)
  - **Attachments on edit.** `attachments` **appends** to the draft's existing attachments (they are kept). Remove specific ones with `removeAttachments` (pass the `blobId` from `get_email_attachments`; a unique attachment name also works — a ref matching nothing, or a name matching more than one, is rejected; a name containing a comma has to go in an array, since the string form splits on every comma). Remove all with `clearFields:['attachments']`. Passing `attachments` together with `clearFields:['attachments']` is rejected as a conflict. Both removal routes reach **everything `get_email_attachments` lists**, embedded body images included, and both are rejected when the surviving body would still reference what they took away — so drop the `<img>` from the body you supply in the same call. See [Sending attachments](email.md#sending-attachments).
  - **Empty values are rejected.** Passing an empty string or empty array for a field whose value would replace what the draft stores (e.g. `subject: ""`, `to: []`) is an error, not a silent clear — it's almost always an accidental clobber. To deliberately blank a field, name it in `clearFields`.
  - **`clearFields`**: list of field names to clear to empty/none. Allowed: `to`, `cc`, `bcc`, `replyTo`, `subject`, `textBody`, `htmlBody`, `attachments`, `forwardedMessageId`. `from` cannot be cleared (a draft always has a sender, matching the Fastmail UI). You cannot both pass a field as a value and list it in `clearFields`. Clearing `textBody` or `htmlBody` requires `bodyHash`. `clearFields:['forwardedMessageId']` **de-forwards** the draft: it drops the recorded `X-Forwarded-Message-Id`, so `send_draft` will not mark the original forwarded. On a forward draft it drops the recorded `sourceEmailId` too — that pointer names the exact instance the marking is about, so it goes with it; on a *reply* draft it is kept, since the draft is still a reply to that instance. Clearing is metadata, so it works on a body edit and a metadata-only edit alike — and it does not touch the body, so a forwarded-message block already in there stays until you replace the body yourself. **The converse also holds, and it is the easier one to get wrong:** deleting the forwarded-message block from the body by hand does *not* de-forward the draft. The marking lives in the header, so `send_draft` still marks the original forwarded until you name the field here. A cleared draft is still a valid draft; it just may not be sendable (e.g. with no recipients).
  - **The text body is an auto-managed fallback of the HTML.** Editing `htmlBody` alone **regenerates** `textBody` from the new HTML (so an html-alone edit discards any custom `textBody` the draft had — the result says so). Editing `textBody` alone while `htmlBody` is present is **rejected** — it would not change what recipients render (the HTML), and the fallback is managed automatically; to change the message edit `htmlBody`, or supply both bodies to store a custom plain-text alternative. `clearFields:['textBody']` while `htmlBody` is present is **rejected** for the same reason; use `clearFields:['htmlBody']` to convert the draft to a plain-text email. A subject/recipient-only edit (no body written) leaves both bodies untouched. An edit that would leave the draft with no body at all is **rejected**.
  - **The body is stored exactly as written.** Whatever you hand back is what the draft holds, character for character. This server appends nothing, removes nothing, and recognises nothing in it; the one exception is opt-in and explicit (`expandSignature: true`, below). So a reply's quoted original or a forward's forwarded-message block survives an edit **because you handed it back** — read the draft, change the words, send the whole body — and a body sent without it drops it, with no challenge and no warning.
  - **Editing part of the body: `bodyEdits`** ([#177](https://github.com/JonathanGodley/fastmail-mcp/issues/177)). To change a few words without handing the whole body back, pass `bodyEdits: [{find, replace}, ...]`. Each `find` is matched raw and exactly against the body as `get_email` returns it (the HTML when the draft has one, markup and entities such as `&amp;` included, else the plain text) with no whitespace normalisation, and must occur **exactly once**: no match ("not found; re-read the draft"), two or more, overlapping occurrences included ("ambiguous; include more context"), an empty `find`, and two ops whose matches overlap are each **rejected**. Every op is located in the stored body before any is applied, so no op sees another's replacement; an empty `replace` deletes the match. Everything outside the matches, quoted history and embedded images included, is kept byte for byte. From there the edit is an `htmlBody` (or, on a text-only draft, a `textBody`) edit of the spliced result: the text fallback regenerates, an image whose `cid:` reference a `replace` deleted comes off or becomes an attachment as above, and the next `bodyHash` comes back. It cannot be combined with `textBody`, `htmlBody` or clearing either, and needs `bodyHash`. Under `expandSignature: true` only a `{{signature}}` written in a `replace` counts and expands; one already in the stored body is left alone. The result lists each op's matched offset in the pre-edit body and its matched and replacement sizes, in the `chars` (UTF-16 code units) the replaced-draft sizes use.
  - **Proving your copy is current: `bodyHash`.** Because a body edit rewrites the stored body, one written from a stale copy silently overwrites whatever changed in between. So every edit that writes `textBody`/`htmlBody`, applies `bodyEdits`, or clears a body must pass `bodyHash` — the value `get_email` returns for that draft, or the one the `draft_email` or `edit_draft` result that saved it carries. A missing or stale hash is **rejected**; re-read the draft and edit from that. It is a lost-update guard and nothing more: it proves nothing changed the body since the read or write that issued the hash, never that you kept any of it, so it passes on an edit that replaces the body entirely. A metadata-only edit is body-invariant and needs none — but an attachment edit can still **stale a hash you are holding**, because the hash covers the parts the draft's **body lists** carry. `removeAttachments` taking off a part the server had routed into a body list (an embedded image, typically) changes what the hash is taken over with no body written; taking off a part that only ever sat in the attachments list changes nothing the hash covers. **Adding** one may go the same way if the server routes the new part into a body list — this server always writes attachments to the attachments list and does not decide where a later read surfaces them, so treat that direction as unconfirmed. Nothing is lost either way: your next *body* edit is rejected and you re-read. A successful body edit hands the **next** hash back in its result, read off the saved draft, so a run of edits needs no read between each pair, and none at all when it starts from a `draft_email` result. When a hash cannot be issued honestly the result says which case it hit and you re-read: the surviving body is one this server derived from HTML rather than one you supplied (clearing `htmlBody` on a draft that never had one leaves your own stored text standing, so that edit *does* get a hash), or the read-back failed. A third group ends in recreating the draft rather than re-reading it: where the saved draft is one `get_email` would withhold a hash from for good (the three recreate reasons under `bodyHashWithheld` in [Email fields](responses.md#email-fields)), no tool issues one ([#180](https://github.com/JonathanGodley/fastmail-mcp/issues/180)). A returned hash always comes from re-reading the saved message — never from the bytes the call sent.
  - **Expanding a signature: `expandSignature`.** Off by default, so nothing this server finds in a body can make it rewrite one (see [Signing a message](email.md#signing-a-message) for why). Pass `expandSignature: true` and a `{{signature}}` you wrote (in the body, or in a `bodyEdits` replace) is replaced with the sending identity's configured sign-off, and the result shows the join around it, with the stored lines either side as they are (see [Signing a message](email.md#signing-a-message)). `{{quote}}` and `{{forward}}` never expand here and are stored as the literal text you typed — this tool never places history for you. Passing the flag with no `{{signature}}` in the body is rejected, as is the same token twice in one part. A near-miss spelling (`{{Signature}}`, `{{{signature}}}`) is stored as written and **reported** rather than refused, since it may be text the original's author wrote. **A `{{…}}` naming no token at all (`{{sig}}`) is reported too**, on flagged and unflagged edits alike, because this tool stores what you wrote and a mistyped token ships with its braces showing. A `{{signature}}` you store on an *unflagged* edit is reported the same way, and is how you keep one as literal text. **Every one of these notes is count-rise**: a `{{signature}}`, a near-miss, a `{{quote}}`/`{{forward}}`, an escaped spelling or a `{{…}}` naming no token that the draft's **stored** body already carried passes in **silence**, and only what *this* edit added is named. **A note that names a spelling rather than a part is said once for the whole edit**, however many times you wrote it and whether it went into one supplied body or both — one typo is one thing to fix. To write the braces as text *under the flag*, escape them: `\{{signature}}` (in JSON, `"\\{{signature}}"`). The backslash is consumed and the bare token is stored, so it will not expand again unless a later edit passes the flag too. An escaped `{{quote}}` or `{{forward}}` is stored as written, backslash included, like the tokens themselves. On an unflagged edit there is nothing to escape — that body is stored byte for byte, backslash included — and the result says so when *this* edit added the escape, because a backslash you meant as an escape has just shipped as content.
- **send_draft**: Send an existing draft email — **the only tool that transmits a composed message** (see the draft-first note above; calendar invitations are sent by the server, outside compose — see [Calendar invitations send mail](calendar.md#calendar-invitations-send-mail)). The draft must have recipients and a from address, and that address must be a real one: a draft whose stored From is a **[wildcard pattern](#email-tools)** (`*@example.com`) is refused, because the asterisk would go out as the sender — edit the draft with an explicit `from` first. **It must also be in the Drafts folder** — a draft moved to Archive, to Trash or to any other folder is **rejected**, and the refusal says where it is now; move it back to Drafts with `move_email` and send it again. A draft that is in Drafts *and* carries another label is still in Drafts and sends normally, and **keeps that label**: the send files the message into Sent by **patching** `mailboxIds` — naming just those two mailboxes, removing Drafts and adding Sent — so every other label the draft carried, and any Inbox membership, survives the send untouched. Both the Drafts folder it must be in and the Sent folder it is filed into are resolved by their **role**, not by name, so a custom folder called "Draft notes" or one called "Sent" satisfies neither; if no mailbox in the account carries the `drafts` role, or none carries the `sent` role, `send_draft` refuses rather than sending unchecked or sending with nowhere to file the sent copy. Both refusals come **before** the submission, so nothing is transmitted. A third refusal covers the case where the server returns the draft with **no readable filing at all** — it carries its own message, names no location and suggests no move, because the draft's whereabouts are unknown rather than known to be wrong. An **HTML-only draft with real content** sends as-is — HTML-only mail is valid. That is a draft whose HTML yields no derivable text at all, e.g. one showing a remote image with no alt text; a draft displaying an embedded (`cid:`) image is not in that group, since it derives `[image]` and carries a text part. Only a **genuinely empty body part** (e.g. a blank `htmlBody` alongside real text, which can happen for drafts created in other clients) is **rejected**: an empty `text/html` part renders blank and shadows a real `text/plain`, so the recipient would see nothing. Edit the draft to supply or clear that body first. **Every** body part is checked, so a blank one is rejected wherever it sits in the draft's body list and whether or not it declares a content type — a part that declares none counts as the body of whichever list carries it, which is how a recipient's client renders it, so a blank one renders blank just the same. (Drafts created by this server never carry an empty part; every send/draft path drops empty bodies on write.)
  - Parameters: `emailId` (required)
  - **The result reports what went out.** It says how many embedded (`cid:`) images the transmitted message carried, read off the draft as submitted. That is a **receipt, not a check** — `send_draft` never refuses a draft over its images ([#13](https://github.com/JonathanGodley/fastmail-mcp/issues/13)).
  - **Thread state is maintained on send** ([#60](https://github.com/JonathanGodley/fastmail-mcp/issues/60)). Because every reply and forward is transmitted here, this is where the marking happens: a draft carrying `In-Reply-To` marks that original **answered and read**, and a draft carrying `X-Forwarded-Message-Id` (set by `draft_email`, on both inline and `asAttachment` forwards) marks that original **forwarded and read**. A draft with both — which this server never writes — is treated as a reply. A draft that records neither header marks nothing (an ordinary compose).
  - **Which copy gets marked.** A Message-ID names a *message*, but an account can hold several stored copies of one (a duplicate delivery, or a self-addressed message filed into another folder). Drafts made by `draft_email`'s `reply`/`forward` modes record the JMAP id of the exact copy they were composed from (an `X-Fastmail-MCP-Source-Id` header on the draft, surfaced as `sourceEmailId` by `get_email` so the copy to be marked is inspectable before sending), and that copy is what gets marked — validated first: the recorded instance must still exist and still carry the draft's source Message-ID, otherwise it falls back. The fallback (drafts without the record — older drafts, foreign clients) resolves the Message-ID by lookup: when it matches exactly one stored message, that one is marked; **no** match, or more than one, marks nothing and the result says which message went unmarked and why — rather than guessing at one. All of this happens **after** submission and can never fail or undo the send: the mail is already gone. (The recorded header is transmitted with the message; it is an opaque account-scoped id, disclosing less than the `In-Reply-To` beside it — see [`docs/security-model.md`](../security-model.md).)
- **search_emails**: Email search. Free-text `query` matches subject/body/participants (plain words, **not** operator syntax — `from:alice@example.com` is matched literally; use the dedicated `from`/`to`/`cc`/`bcc`/`subject` params instead). All filters combine with AND. **Trash and Spam are excluded by default** (set `includeTrash`/`includeSpam`); drafts are included. `query` is optional — with no query it returns recent mail matching only the structural filters. When a Trash/Spam match is withheld, a trailing note reports how many — so no note means nothing filed only in Trash/Spam matched, and you need not re-search to check. `isAnswered`/`isForwarded` test a mark kept per stored copy: replying marks only the copy replied to, so other copies of that message (a duplicate delivery, a copy in another folder) and earlier messages in the thread still match `isAnswered: false`. Any client on this account that sets IMAP `\Answered` sets the mark, but a reply sent by something that never sets it on this mailbox is not recorded.
  - Parameters: `query` (optional), `from` (optional), `to` (optional), `cc` (optional), `bcc` (optional), `subject` (optional), `hasAttachment` (optional), `isUnread` (optional), `isPinned` (optional), `isAnswered` (optional — true: only messages marked replied-to; false: only messages without the mark, which also matches your own sent mail, drafts and newsletters, so pair it with `mailbox: "inbox"`), `isForwarded` (optional — true/false: only messages with/without the forwarded mark), `mailbox` (optional — id/role/name/path; scoping ignores the default exclusion; a blank value is rejected - omit it instead), `requiredMailboxes` (optional array — see [Scoping across several mailboxes](email.md#scoping-across-several-mailboxes)), `excludeMailboxes` (optional array — same section), `after` (optional date or datetime), `before` (optional date or datetime), `limit` (default: 20, max: 100), `position` (optional offset — see [Result counts and paging](responses.md#result-counts-and-paging-position)), `ascending` (optional, oldest first), `excludeDrafts` (optional), `includeTrash` (optional), `includeSpam` (optional), `fields` (optional array — return only these fields; the way to keep a many-message sweep inside one response, and `sentAt` is returned only when named here, see [Field projection](responses.md#field-projection-fields)), `raw` (optional, return original JMAP response)
  - **`requiredMailboxes` / `excludeMailboxes`** scope across several mailboxes at once, and are the only place this server does — see [Scoping across several mailboxes](email.md#scoping-across-several-mailboxes) for what exclusion actually means here (it is weaker than the name suggests).
  - **`hasAttachment` filters on the server's own heuristic**, compared directly (RFC 8621 §4.4.1) — it is the same value the results report, not a count of parts. It answers "is there content attached", so a message whose only image is a small embedded one is filtered *out* by `hasAttachment: true`. There is no server-side filter for embedded images: narrow with the other filters, then read the parts with `get_email`.
  - **Date bounds (`after` / `before`).** Both accept a plain date (`2026-07-20`) or a full datetime (`2026-07-20T14:30:00Z`, or with an offset such as `2026-07-20T14:30:00+01:00`); a datetime with no zone is read in the **configured time zone** (see [Calendar window dates](calendar.md#calendar-window-dates); the tool descriptions name the zone in use). A date-only value means **midnight at the start of that day in that zone**, so `after:"2026-07-20"` includes all of your July 20 while `before:"2026-07-20"` (the bound is exclusive) excludes it — pass `before:"2026-07-21"` to search up to and including July 20. Only those two shapes are accepted: an unpadded or slash-separated date (`2026-7-20`, `2026/07/20`), free text (`20 July 2026`), a partial date (`2026-07`), a day that doesn't exist in its month, and an empty string are all **rejected** with a message naming the parameter — omit the parameter to search without that bound. The strictness is deliberate: the loose forms would be read by a fallback parser as host-local midnight rather than in the configured zone, which would silently move the search window ([#70](https://github.com/JonathanGodley/fastmail-mcp/issues/70)).
- **mark_email_read**: Mark an email as read or unread
  - Parameters: `emailId` (required), `read` (default: true)
- **pin_email**: Pin or unpin an email
  - Parameters: `emailId` (required), `pinned` (default: true)
- **delete_email**: Delete an email (move to trash). The move to Trash writes `mailboxIds` whole-value, replacing the entire membership, so it **drops the message's other labels** and the Trash copy cannot show you what they were ([#123](https://github.com/JonathanGodley/fastmail-mcp/issues/123)). No keyword is written, but the reported read state can still flip to read (see [archiving](email.md#archiving-does-what-the-fastmail-client-does)).
  - Parameters: `emailId` (required)
- **move_email**: Move an email to a different mailbox. **Replaces the message's entire mailbox membership** - every other label or folder it was filed under is removed. To file it somewhere while keeping those, use `add_labels` - which takes the Inbox and the account's own labels only, so a folder is reachable by moving alone (archiving is the exception: `archive_email` keeps the rest of the filing). No keyword is written, but the reported read state can still flip to read (see [archiving](email.md#archiving-does-what-the-fastmail-client-does)).
  - Parameters: `emailId` (required), `targetMailbox` (required — [id, role, name, or path](email.md#naming-a-mailbox))
- **archive_email**: Archive one or more emails the way the Fastmail client does - **remove the Inbox membership and leave everything else in place**, adding the Archive folder only when doing that would leave the message filed nowhere. It handles a batch, so there is no `bulk_archive`. It writes **no keyword**, which is not the same as leaving the read state untouched - see the caveat in the section linked below. Once a message has **left the Inbox** it **refuses** one in Trash, Spam, Drafts, Scheduled, Sent or Snoozed, because the client offers no Archive action there either. The Inbox is tested first, so a message in the Inbox *and* one of those is archived rather than refused, keeping that membership - except that a message also in Scheduled may come back as `failed`, because the server appears to reject re-asserting a scheduled membership outside a send request ([#130](https://github.com/JonathanGodley/fastmail-mcp/issues/130)). The destination is found by JMAP `archive` role, never by folder name, so a folder merely *named* "archive" is not it. For any other destination use `move_email`. Full behaviour, including the six per-message outcomes it reports: [Archiving does what the Fastmail client does](email.md#archiving-does-what-the-fastmail-client-does) ([#21](https://github.com/JonathanGodley/fastmail-mcp/issues/21), [#104](https://github.com/JonathanGodley/fastmail-mcp/issues/104)).
  - Parameters: `emailIds` (required array of **message** ids, not thread ids — pass an array even for one message; duplicates are collapsed; to archive a conversation pass every message id in it).
- **add_labels**: Add labels (mailboxes) to an email without removing existing ones. Labels means the **Inbox and the account's own labels**; a folder (any other role mailbox) is rejected - use `move_email`. Adding the inbox label is how a message is put back in the Inbox
  - Parameters: `emailId` (required), `mailboxes` (required array - each entry [id, role, name, or path](email.md#naming-a-mailbox), resolved like every other mailbox tool; any unresolved or ambiguous entry rejects the whole call with the valid list, as does any entry that resolves to a folder rather than a label)
- **remove_labels**: Remove specific labels (mailboxes) from an email. Labels means the **Inbox and the account's own labels**; a folder (any other role mailbox, Archive included) is rejected before anything is written - use `move_email`. Removing the inbox label archives the message the way `archive_email` does, with its caveats: it acts on this message, not its conversation, and no keyword is written, but dropping an unread Inbox copy can flip the reported read state to read (see [archiving](email.md#archiving-does-what-the-fastmail-client-does)). Removing the message's last label archives it instead of leaving it filed nowhere
  - Parameters: `emailId` (required), `mailboxes` (required array - each entry [id, role, name, or path](email.md#naming-a-mailbox), resolved like every other mailbox tool; any unresolved or ambiguous entry rejects the whole call with the valid list, as does any entry that resolves to a folder rather than a label)

### Advanced Email Features

- **get_email_attachments**: List an email's parts as **raw JMAP part objects** (`partId`, `blobId`, `type`, `size`, `name`, `disposition`, `cid`) rather than the simplified shape the read tools return. An `emailId` that matches no message is refused (`InvalidParams`), not answered with an empty list. Like `get_email`, the listing includes images embedded in the message body, not only "attached" files. Nothing in this raw listing distinguishes the two — a body-embedded part usually reports `disposition: null` — so cross-check `get_email`'s derived `isInline` before acting on an entry, for instance before handing its `blobId` to `edit_draft`'s `removeAttachments`, which would strip an image the body still displays. This listing is where an `attachmentId` comes from: pass an entry's `partId` or `blobId` back to `download_attachment`, or to an `attachments` item that attaches that part to a new message (`emailId` + `attachmentId`, which needs `FASTMAIL_ALLOW_BLOB_ATTACH` — see [Sending attachments](email.md#sending-attachments)). This listing is also what `download_attachment`'s entry numbers count from: its first entry is `attachmentId: "0"`.
  - Parameters: `emailId` (required), `raw` (optional)
  - **`raw` here is a SET escape, not a shape escape.** The entries are already raw JMAP objects, so `raw: true` changes only *which* parts are listed: it returns the JMAP `attachments` array alone, dropping the body-routed parts. How many were withheld is reported as a **separate second message**, never appended to the JSON, which stays parseable. `download_attachment` entry numbers always count from the full listing, so a `raw` listing is not an index basis.
- **download_attachment**: Download an email attachment. If path is provided, saves the file to disk and returns the file path and size. A file already at that path is **overwritten** without asking, and the result then says it replaced an existing file. Otherwise returns a download URL.
  - Parameters: `emailId` (required), `attachmentId` (required), `path` (optional)
  - **`attachmentId` accepts four forms**, resolved in this fixed order: a `partId` from `get_email_attachments`; a `blobId`; `cid:<value>` for an embedded image, using the `cid` from `get_email`; or a plain entry number (`0`, `1`, `2`, …) counting from the start of the `get_email_attachments` listing. Digits resolve as a **partId first** — Fastmail partIds are themselves digit strings — so the entry-number form applies only when no part claims that value. The `cid:` prefix is required for the cid form (a bare Content-ID is not one), only the first prefix is stripped (`cid:cid:x` looks up the Content-ID `cid:x`), the value is matched literally before any percent-decoding is tried, and a value matching more than one part is **rejected** rather than guessed at. A number with anything else in it (`3a`, `-1`, `1.5`) is rejected rather than silently read as an entry number. Entry numbers are positional and shift whenever the listing does, so prefer a `partId` or `blobId` for a reference you will reuse (a cid the server minted is not durable). **The entry-number form is read-only**: the same grammar is accepted by an `attachments` item that attaches a part to outgoing mail, and there a reference that resolved *only* by entry number is rejected — a wrong download costs a retry, while a wrong attach is baked into a draft you may then send.
  - `path` here is a **destination written** under `FASTMAIL_DOWNLOAD_DIR` — the opposite direction from the compose tools' `attachments[].path`, which is a **source read** under `FASTMAIL_ATTACH_DIR`. It may be absolute or relative. Relative paths (including a bare filename) resolve against the download directory, so an attachment lands there in one step. Absolute paths must fall within that directory; traversal or symlink escape outside it is rejected. To save directly into your own location, set `FASTMAIL_DOWNLOAD_DIR` to that root (see [Setup](configuration.md#configuration)) — confinement stays on, scoped to the directory you choose. Parent directories under that root are created as needed.
- **get_thread**: Get all emails in a conversation thread. Returns metadata + preview for each email, or the full plain-text bodies with `includeBodies`.
  - Parameters: `threadId` (required), `includeDrafts` (optional, include in-progress drafts), `includeBodies` (optional, return each message's `bodyText`), `stripQuoted` (optional, requires `includeBodies` — return each message's new text only), `fields` (optional array — return only these fields per message, see [Field projection](responses.md#field-projection-fields)), `raw` (optional, return original JMAP response)
  - `includeBodies` turns an N-message conversation read into one call — see [Reading long threads cheaply](email.md#reading-long-threads-cheaply).
  - Draft messages are **excluded by default** (an in-progress reply is noise when reading a conversation). When any are present, a trailing note reports **how many drafts are hidden** (so a draft reply you already started isn't missed) — the drafts themselves are not surfaced. Set `includeDrafts: true` to include them. (The note is on the simplified path only; `raw` output stays pure JSON, so a raw consumer passes `includeDrafts` itself.)

### Email Statistics & Analytics

- **get_mailbox_stats**: Get statistics for a mailbox (unread count, total emails, etc.)
  - Parameters: `mailbox` (optional — [id, role, name, or path](email.md#naming-a-mailbox); defaults to all mailboxes; a blank value is rejected - omit it instead)
- **get_account_summary**: Get overall account summary with statistics: mailbox and identity counts, and each mailbox's `totalEmails`/`unreadEmails`. The top-level `totalEmails`, `unreadEmails`, `totalThreads` and `unreadThreads` are the **sum of every mailbox's own counts**, Trash and Spam included, so a message filed in several mailboxes (a label) is counted once per mailbox: they are not the number of distinct messages or threads in the account.

### Bulk Operations

- **bulk_mark_read**: Mark multiple emails as read/unread
  - Parameters: `emailIds` (required array; duplicates are collapsed), `read` (default: true)
- **bulk_pin**: Pin or unpin multiple emails
  - Parameters: `emailIds` (required array; duplicates are collapsed), `pinned` (default: true)
- **bulk_move**: Move multiple emails to a mailbox. **Replaces each message's entire mailbox membership** - every other label or folder each one was filed under is removed. To file them somewhere while keeping those, use `bulk_add_labels` - which takes the Inbox and the account's own labels only, so a folder is reachable by moving alone (archiving is the exception: `archive_email` keeps the rest of the filing). No keyword is written, but the reported read state can still flip to read (see [archiving](email.md#archiving-does-what-the-fastmail-client-does)).
  - Parameters: `emailIds` (required array; duplicates are collapsed), `targetMailbox` (required — [id, role, name, or path](email.md#naming-a-mailbox))
- **bulk_delete**: Delete multiple emails (move to trash). Each move to Trash writes `mailboxIds` whole-value, replacing the entire membership, so it **drops each message's other labels** and the Trash copy cannot show you what they were ([#123](https://github.com/JonathanGodley/fastmail-mcp/issues/123)). No keyword is written, but the reported read state can still flip to read (see [archiving](email.md#archiving-does-what-the-fastmail-client-does)).
  - Parameters: `emailIds` (required array; duplicates are collapsed)
- **bulk_add_labels**: Add labels to multiple emails simultaneously. Labels means the **Inbox and the account's own labels**; a folder (any other role mailbox) is rejected - use `bulk_move`
  - Parameters: `emailIds` (required array; duplicates are collapsed), `mailboxes` (required array - each entry [id, role, name, or path](email.md#naming-a-mailbox), resolved like every other mailbox tool; any unresolved or ambiguous entry rejects the whole call with the valid list, as does any entry that resolves to a folder rather than a label)
- **bulk_remove_labels**: Remove labels from multiple emails simultaneously. Labels means the **Inbox and the account's own labels**; a folder (any other role mailbox, Archive included) is rejected before anything is written - use `bulk_move`. The last-label archive fallback is decided per message, so one batch can archive some and merely unlabel others. A rejection is not, and aborts the whole batch before anything is written: a folder or unknown mailbox named as a label, a message whose current filing the server does not report, or a message that would need an Archive the account does not have. An email id the server does not know, or a per-message failure at the server, is different: the other messages **are** written, and the error names the failures and says how many were written
  - Parameters: `emailIds` (required array; duplicates are collapsed), `mailboxes` (required array - each entry [id, role, name, or path](email.md#naming-a-mailbox), resolved like every other mailbox tool; any unresolved or ambiguous entry rejects the whole call with the valid list, as does any entry that resolves to a folder rather than a label)

There is **no `bulk_archive`**. `archive_email` already takes an `emailIds` array and handles a batch in one call, reporting each id's outcome separately - see [Archiving does what the Fastmail client does](email.md#archiving-does-what-the-fastmail-client-does). Reaching for `bulk_move` with a target of `"archive"` instead does the wrong thing: it replaces each message's whole membership, dropping every label. Its destination is also resolved [the ordinary way](email.md#naming-a-mailbox), which falls through to matching on name; `archive_email` and `delete_email` do not, resolving by role and nothing else, so a folder named after a role can never become their destination on any account.

### Contact Tools

All three read tools carry `kind` on a card that is not an ordinary person - see [`kind` tells you which cards the write tools will refuse](contacts.md#kind-tells-you-which-cards-the-write-tools-will-refuse).

- **list_contacts**: List all contacts, one page at a time (see [Result counts and paging](responses.md#result-counts-and-paging-position)). Returns simplified format by default. Pages follow one fixed order: first name, then surname, then the card's uid as a tiebreak. Names are compared byte by byte, so the order is case-sensitive: an unaccented capital sorts before every lowercase letter, and accented letters sort after both. Cards with no first name come first.
  - Parameters: `limit` (default: 20, max 100), `position` (optional, 0-based offset; pass back the `nextPosition` from the previous page), `verbose` (optional, include all fields), `raw` (optional, return original JMAP response)
- **get_contact**: Get a specific contact by ID. Returns simplified format by default. Throws if the ID is not found.
  - Parameters: `contactId` (required), `verbose` (optional, include all fields), `raw` (optional, return original JMAP response)
- **search_contacts**: Search contacts by name or email, one page at a time, in the same order as `list_contacts`. Returns simplified format by default.
  - Parameters: `query` (required), `limit` (default: 20, max 100), `position` (optional, 0-based offset; pass back the `nextPosition` from the previous page), `verbose` (optional, include all fields), `raw` (optional, return original JMAP response)
- **create_contact**: Create a contact. Needs at least a name or one email address. Returns the created card, read back after the write, in the same shape `get_contact` returns. If only that read-back fails, the contact was still created: the result is `{id}` with a note saying so, and creating it again would make a duplicate. See [Writing contacts](contacts.md#writing-contacts) for the accepted entry shapes.
  - Parameters: `name` (full-name string or `{given?, surname?, full?}`), `emails` (array; bare address strings or `{address, label?}`), `phones` (array; bare number strings or `{number, label?}`), `addresses` (array of `{full, label?}` objects), `notes`, `addressBookId` (optional, defaults to the account's address book), `verbose`, `raw`
- **update_contact**: Update a contact, **merging per entry** so the stored fields the simplified output doesn't show (`contexts`, `pref`, …) survive an edit. Returns `{contact, previousCard}`. An edit that both drops a stored entry and adds an unknown one is rejected as ambiguous unless `allowEntryReplace` is set (which is scoped to that one array); `addresses` replace wholesale; `name` merges into the stored components; a changed label is added, never removed. Refused, with nothing written, if the address book changed after the tool read the card (retry the call). See [Writing contacts](contacts.md#writing-contacts).
  - Parameters: `contactId` (required), `name`, `emails`, `phones`, `addresses`, `notes` (same shapes as create; `[]` or a blank string is rejected — use `clearFields`), `clearFields` (array of `"emails"`/`"phones"`/`"addresses"`/`"notes"`; `name` is not clearable), `allowEntryReplace` (boolean), `verbose`, `raw` (both apply to `contact` only — `previousCard` is always the raw card)
- **delete_contact**: Delete a contact. **Irreversible** — a card does not go to Trash. Returns `{deleted, deletedCard}`, the id plus the full card as it stood immediately before the destroy, so a wrong delete is at least visible in full. `create_contact` can rebuild the name, emails, phones, addresses and note from it, but not the rest of the card — see [Writing contacts](contacts.md#writing-contacts). A card whose `kind` is not `individual` (a contact **group**, an org, ...) is refused, because this server cannot create one and so cannot put one back. Refused, with nothing deleted, if the address book changed after the tool read the card (retry the call). There is deliberately no confirmation parameter.
  - Parameters: `contactId` (required)

### Calendar Tools

- **list_calendars**: List all calendars. Each entry carries `id`, `displayName`, `url`, and `description`/`color` when set. A calendar's `id` **is** its CalDAV URL, and every `calendarId` parameter accepts either that or the calendar's display name. Prefer the `id` when it matters: a display name is not unique per account, and one that matches two calendars is refused everywhere it is accepted ([#173](https://github.com/JonathanGodley/fastmail-mcp/issues/173)).
  - **A collection the server failed to describe is named, not dropped** ([#136](https://github.com/JonathanGodley/fastmail-mcp/issues/136)). When an entry inside the account's calendar home comes back broken - a failed response element, or a failed `propstat` that strips its properties - it cannot appear as a row, because the failure destroys its display name and its `resourcetype` together. The response instead carries a trailing `Note:` line giving its path, and the subject counts them - the line *opens* `Note: a collection in the calendar list failed to list:` for one and `Note: 3 collections in the calendar list failed to list:` for several, then runs on past the path with what that failure does and does not mean. If you are matching on it, match the `in the calendar list failed to list` phrase rather than the singular sentence. **The note does not claim it was a calendar**, and neither should you: nothing survives the failure to say what kind of collection it was, so the honest statement is that a collection could not be listed and this listing is the ones that did answer. The same note appears on `list_calendar_events` and `get_calendar_event`; `create_calendar_event` refuses it as a target; `update_calendar_event`/`delete_calendar_event` act on the copy they found and name what they could not look in.
  - **Detection happens when the list is built, and a list built while one was broken is never cached.** So the next calendar call re-asks the server, and the note goes away by itself once the collection recovers. The residual, stated plainly: a *healthy* list **is** cached for the life of the process, so a calendar that breaks **after** a successful discovery keeps being listed here until the server restarts.
- **list_calendar_events**: List calendar events (core fields only — no participants for token efficiency), one entry per occurrence in the requested window ([#64](https://github.com/JonathanGodley/fastmail-mcp/issues/64), [#100](https://github.com/JonathanGodley/fastmail-mcp/issues/100)).
  - Parameters: `calendarId` (optional; the `id`/URL or the display name from `list_calendars`, omit to read every calendar), `startDate` (optional, see [Calendar window dates](calendar.md#calendar-window-dates)), `endDate` (optional, same), `limit` (default: 50, hard cap 100), `position` (optional offset, see [Result counts and paging](responses.md#result-counts-and-paging-position))
  - **Recurring events are expanded.** Give a `startDate`/`endDate` window and the server applies each recurrence rule, returning one entry per occurrence *inside that window* with `start`/`end` set to the occurrence's real dates. A fortnightly event across three months is seven entries, not one. **There is no unwindowed call**: omit both bounds and you get the next month - the start of today in the configured timezone, for 31 days - expanded like any other window, with a trailing `Note:` naming the range actually searched ([#142](https://github.com/JonathanGodley/fastmail-mcp/issues/142)). To see a series unexpanded, at its original start date and with its `RRULE` intact, call `get_calendar_event` on the row's `id`.
  - **Four fields say what a date is**: `recurrenceId` present means `start`/`end` **are** the in-window occurrence; `recurrenceRule` present (the raw `RRULE`) means this is the series **master**, shown at its **original** start date, which may be years before the window; `recurrenceDates` present (the raw `RDATE` values, comma-separated) says the same for a series that **lists** its occurrences instead of stating a rule; `isRecurring` says the entry belongs to a repeating series, and on a row read out of a VEVENT its absence says it does **not** - the field is decided there rather than omitted when the evidence is thin. One kind of row makes no recurrence claim in either direction: a stored record this server can read no VEVENT out of still produces a row, titled `Untitled` and carrying no dates, and `isRecurring` is absent on it because nothing was established about it. **`recurrenceDates` carries the values and not the parameters** - a `TZID`, `VALUE=DATE` or `VALUE=PERIOD` on the `RDATE` line is dropped - so a designator-less value in that list does **not** follow the `timeZone` rule that governs `start`, and RDATEs written in different zones are indistinguishable once joined into one list. It is proof that other dates exist, not a date you can place on a clock; pass a window and let the server expand the series if you need real occurrence times. Master and occurrence are the usual split, but the two fields *can* appear together — RFC 5545 lets an override block carry its own rule — and where they do, `recurrenceId` names the instance and `recurrenceRule` is that block's own rule rather than the series'. There is one case the expanded output cannot distinguish, and it is the server's doing rather than a choice made here: Fastmail sets a `RECURRENCE-ID` only on instances **after** the first, so a series' first occurrence arrives bare, and a window holding **only** that occurrence yields a block indistinguishable from a one-off. Those blocks are settled before the listing returns, by re-reading the stored records they came from - a stored record still states the repeat the expansion stripped - so `isRecurring` is trustworthy on every row a VEVENT was read for. The extra read is one request per calendar rather than one per row, and is skipped entirely for a calendar with nothing ambiguous in it - but note that a single markerless block is exactly what an ordinary one-off looks like, so on a normal listing nearly every row is ambiguous and its stored payload is fetched a second time. If the read cannot be completed, or answers with a payload holding no readable event, the call **fails** rather than return rows whose recurrence it could not establish ([#155](https://github.com/JonathanGodley/fastmail-mcp/issues/155)).
  - **A one-sided window is bounded to 31 days.** Pass only `startDate` (or only `endDate`) and the missing half is filled in a month away, then the response carries a trailing `Note:` naming the range actually searched. Name both bounds to choose the span yourself; see [Calendar window dates](calendar.md#calendar-window-dates).
  - **One series too dense for the window fails the whole call.** If any single repeating event expands to more than 5000 occurrences in the range searched (`CALENDAR_MAX_OCCURRENCES_PER_SERIES`), the call returns an error naming that event - title, id, occurrence count and calendar - instead of a listing, even though every other event was fine. Narrow the window so it covers fewer of that event's occurrences, or pass a `calendarId` that does not hold it. Why 5000, and why a refusal rather than a note: [docs/conventions.md](../conventions.md#the-span-is-the-callers-the-density-is-not).
  - **Pages walk one earliest-first list.** Every target calendar is queried, and only then is the combined set sorted by start time and cut at `position`. Rows sharing a start time always come back in the same order, so an unchanged calendar pages without overlap or gap. The sort compares *instants*, not the text of the dates (see [Calendar times: a name, never an offset](calendar.md#calendar-times-a-name-never-an-offset)).
  - **Every occurrence row of a series carries the SAME `id`, and it names the series — which is why the write tools refuse it.** Seven rows of a fortnightly event are seven identical ids, and acting on one would act on all seven. So `update_calendar_event` and `delete_calendar_event` **reject** any id that resolves to a repeating event, with no override parameter (see [Repeating events cannot be changed or deleted here](calendar.md#repeating-events-cannot-be-changed-or-deleted-here)). Change or remove a repeating event, or a single occurrence of one, in the Fastmail web interface. A row's **`url` is the same record under another name**, and passing it in place of `id` reaches the same refusal — the check reads the stored record, not the shape of the argument. It is kept on the row because a UID is unique per collection rather than per account, so where two calendars hold the same UID the `url` is the only thing telling the records apart.
  - **Rows never carry `participants` or `organizer`**, on any event, because this call does not fetch them. Empty fields are omitted throughout, so an absent participant list here cannot be told apart from an event with no attendees at all. Call `get_calendar_event` before anything destructive: it is the only way to see who the server is about to mail.
  - **`transparency` appears on a row only when the event is not busy** — normally `"free"`, or a non-spec token where the record holds one. Most events block your calendar, so a row that says nothing is busy and the field is omitted to keep rows small. The exception is the `"Untitled"` row with no dates that a record with no readable VEVENT produces: nothing was read out of it, so its busy state is unknown, and `get_calendar_event` cannot open it either. For any other row, `get_calendar_event` states it on every event instead — see [Busy and free](calendar.md#busy-and-free-an-all-day-event-is-free-a-timed-event-busy).
  - **Rows are filtered exactly against the window you asked for, and all-day events are your LOCAL days.** A date-only value covers that whole day in the account's configured zone, and a multi-day date span covers all of its days. Three cases still put a row outside the window or keep one out of it ([docs/conventions.md](../conventions.md) has the mechanics): a block still carrying its own `RRULE`/`RDATE` only ever **adds** a row, so check each `start` against the window you asked for; a **floating** timed event that expansion has stamped as UTC can be **absent** from the window it really belongs to; and a series that lists its dates as `RDATE`s and states no `RRULE` returns nothing for a window that misses the series start. **An empty result from this call is therefore not proof of a free day** - on any account, not only one far from UTC.
  - **Paging** works as in [Result counts and paging](responses.md#result-counts-and-paging-position). **Each page re-reads every calendar** in the window, so paging costs a full read per page, and an event added, moved or deleted between calls can repeat or skip a row at a page boundary.
  - **A TOTAL discovery failure is an error, not an empty list; a PARTIAL one is named.** If the CalDAV server fails to list the account's calendars at all, this raises rather than returning `[]` — an empty result to an availability question reads as "you are free", which is the dangerous way to be wrong. A partial failure has three forms and they behave differently ([#136](https://github.com/JonathanGodley/fastmail-mcp/issues/136)):
    1. **Broken inside the calendar-home listing** — detected when the list is built, from the same PROPFIND answer the list came from. This call answers from the calendars that did list and adds a trailing `Note:` line containing `in the calendar list failed to list` (subject `a collection`, or `N collections`) and naming its path. If that collection *was* a calendar, its events are missing from these results **and from the total**, so a quiet answer is not proof of a free day. Nothing is cached while one is outstanding.
    2. **Listed, then failed on read** — a calendar that answered for itself and then failed when its events were fetched fails the **whole call** with an error. There is no "rest of it" to answer from, so no partial listing is returned.
    3. **Not visible to this account at all** — the server omits it from the listing entirely, so nothing on this side can report it.
  - A `calendarId` that matches no calendar raises for the same reason, naming the calendars that do exist: the display name is matched case-sensitively, so `"work"` for a calendar called `"Work"` is a plausible miss. Surrounding whitespace is ignored on both sides, and `list_calendars` reports the trimmed name, so the name it gives you is one this parameter resolves. An **empty or whitespace-only** `calendarId` is such a value, not a way to ask for every calendar — omit the parameter for that. It narrows what the call touches, so it fails closed rather than silently widening to the whole account.
  - **A `calendarId` whose display NAME matches more than one calendar raises too** ([#173](https://github.com/JonathanGodley/fastmail-mcp/issues/173)). A display name is not unique per account — a shared calendar is named by whoever owns it — so rather than answer from every calendar the name matched, this call refuses, naming each match with its URL, and `create_calendar_event` refuses the same value the same way rather than silently writing into the first match. **The URL is the way through**: a calendar's `id`/URL addresses exactly one collection, so the URL form is never ambiguous — not even where another calendar's *display name* is spelled as that URL, which is a decoy anyone sharing a calendar with the account could plant. Same distinction as an ambiguous `eventId` (see [One `eventId` can name more than one record](calendar.md#one-eventid-can-name-more-than-one-record)), with one difference: an event whose UID spells another event's url is listed with that url as its `id`, so the event write tools refuse that url, whereas a calendar's display name is never listed as its `id`.
- **get_calendar_event**: Get a specific calendar event by ID. Returns organizer and participants when available. Throws if the ID is not found. For a repeating event this returns the **series master**: `isRecurring` is set along with `recurrenceRule` (the raw `RRULE`) and/or `recurrenceDates` (the raw `RDATE` values, for a series that lists its occurrences rather than stating a rule), and `start`/`end` are the series' original dates, **not** the next or nearest occurrence — use `list_calendar_events` with a window to get occurrence dates. This unexpanded path is where those fields actually show up: Fastmail strips them from an expanded block (measured for both `RRULE` and `RDATE`). `recurrenceDates` carries the RDATE values without their parameters, with the same caveats as on `list_calendar_events`: it is evidence that other dates exist, not a date you can place on a clock. **And passing a window will not place it on one either, for a series that states no `RRULE`**: Fastmail's window filter matches such a record over its `DTSTART` alone, so a `list_calendar_events` window covering one of these `RDATE` values but not the series start returns nothing at all for it, with no sign in the response that anything was left out ([#167](https://github.com/JonathanGodley/fastmail-mcp/issues/167)). Widen the window until it reaches the series start - the `start` in this response - or confirm the date in the Fastmail web interface. The id is the series id, and `update_calendar_event`/`delete_calendar_event` refuse it - see [Repeating events cannot be changed or deleted here](calendar.md#repeating-events-cannot-be-changed-or-deleted-here). One exception: where a record holds only overridden instances and no master at all, what comes back is one of those overrides and carries a `recurrenceId` — so a `recurrenceId` in this response means you are **not** looking at the master. This path returns the stored `DTSTART`/`DTEND` exactly as written, with `timeZone`/`endTimeZone` naming the zone when it isn't the account's configured one — see [Calendar times: a name, never an offset](calendar.md#calendar-times-a-name-never-an-offset).
  - Parameters: `eventId` (required)
  - **`transparency` is always present here**, as `"busy"` or `"free"` — or, where the record holds a token the spec does not define, that token verbatim. An event whose record carries no `TRANSP` is reported as `"busy"`, **derived** from RFC 5545 §3.8.2.7 rather than read off the record; the event is busy either way. `list_calendar_events` omits the field for every busy event instead. See [Busy and free](calendar.md#busy-and-free-an-all-day-event-is-free-a-timed-event-busy).
- **create_calendar_event**: Create a new calendar event. Supports date-only (e.g. `2026-04-01`) for all-day events. DTEND is exclusive per RFC 5545 — a one-day event on April 1 needs `end: "2026-04-02"`. An all-day event is created **free** and a timed event **busy**, matching the Fastmail client; pass `transparency` to say otherwise — see [Busy and free](calendar.md#busy-and-free-an-all-day-event-is-free-a-timed-event-busy). See [Start/end agreement](calendar.md#startend-agreement) for the form and ordering rules, [Writing calendar times](calendar.md#writing-calendar-times) for `timeZone`, and [Calendar text size limits](calendar.md#calendar-text-size-limits) for the size caps.
  - Parameters: `calendarId` (required; the `id`/URL or the display name from `list_calendars`, matched case-sensitively and resolved exactly as on `list_calendar_events`, surrounding whitespace ignored. A calendar `list_calendars` does not show cannot be written to either, and a name matching **more than one** calendar is refused here exactly as it is on a read, naming each match with its URL rather than writing into the first: pass that calendar's URL, which addresses one collection and cannot be ambiguous), `title` (required; surrounding whitespace is trimmed and a whitespace-only title is rejected, as on update), `description` (optional; trimmed, and an empty or whitespace-only value is rejected, as on update), `start` (required, ISO 8601 or date-only), `end` (required, ISO 8601 or date-only), `location` (optional; trimmed, and an empty or whitespace-only value is rejected, as on update), `timeZone` (optional; IANA zone name for a designator-less `start`/`end` — omitted writes the account's configured zone, see [Writing calendar times](calendar.md#writing-calendar-times)), `transparency` (optional; `"busy"` or `"free"` — omit to take the frame's default, all-day free and timed busy), `participants` (optional array; each entry is `{email, name?}` **or a bare email-address string**. The whole array may also be sent as a JSON string; a comma-joined string is *not* accepted. An unknown per-item key, a missing/non-string `email`, or a non-string `name` is rejected naming its position, e.g. `participants[2]`)
- **update_calendar_event**: Patch an existing calendar event. **Single (non-repeating) events only** — an id that resolves to a repeating event is rejected, and no parameter overrides that (see [Repeating events cannot be changed or deleted here](calendar.md#repeating-events-cannot-be-changed-or-deleted-here)). Preserves all existing data (attendees, reminders, recurrence rules, etc.) not being changed. Omit a field to leave it unchanged, though a call that names no field and no `clearFields` at all is rejected; passing an empty or whitespace-only string for `title`, `description`, or `location` is rejected (it won't silently blank the property). To delete `description`, `location` or the event's statement about free/busy, list them in `clearFields`. A time with no Z/offset keeps the event's stored `TZID`; with none, it stays floating on a floating event and is otherwise read in the configured zone. A new `start`/`end` is checked against the value it will sit beside — see [Start/end agreement](calendar.md#startend-agreement). `timeZone` works differently here than on create — see [Writing calendar times](calendar.md#writing-calendar-times). `transparency` sets or replaces the event's free/busy and `clearFields: ["transparency"]` deletes the property; with neither, an update never changes free/busy at all — not even when it converts the event between all-day and timed hours — see [Busy and free](calendar.md#busy-and-free-an-all-day-event-is-free-a-timed-event-busy). WARNING: providing `participants` replaces ALL existing attendee data; `participants: []` removes all attendees (and the now-orphaned ORGANIZER). The same [text size limits](calendar.md#calendar-text-size-limits) apply as on create.
  - Parameters: `eventId` (required), `title`, `description`, `start`, `end`, `location`, `timeZone` (optional; IANA zone name for a designator-less `start`/`end` you are also passing this call — for the omitted case see [Writing calendar times](calendar.md#writing-calendar-times)), `participants` (array; each entry is `{email, name?}` **or a bare email-address string**, and the whole array may be sent as a JSON string — same rules and same index-naming rejections as on create), `transparency` (`"busy"` or `"free"`; sets or replaces the event's free/busy, and conflicts with naming it in `clearFields`), `clearFields` (array of `"description"`/`"location"`/`"transparency"` to delete — clearing `transparency` removes the property, which leaves the event reading as busy without saying so)
- **delete_calendar_event**: Delete a calendar event. **Single (non-repeating) events only** — an id that resolves to a repeating event is rejected (see [Repeating events cannot be changed or deleted here](calendar.md#repeating-events-cannot-be-changed-or-deleted-here)). **Sends mail** if the event has attendees — the server emails each of them a cancellation (see [Calendar invitations send mail](calendar.md#calendar-invitations-send-mail)).
  - Parameters: `eventId` (required)
  - **A repeating event is refused**, because its `eventId` names the whole series: deleting the row shown for one occurrence would destroy every past and future occurrence and send every attendee a cancellation. Delete it, or one occurrence of it, in the Fastmail web interface; see [Repeating events cannot be changed or deleted here](calendar.md#repeating-events-cannot-be-changed-or-deleted-here).
  - **Irreversible, and only the UID and url are echoed back.** A calendar event does not go to Trash the way an email does, and this tool reads the record only to find it and to refuse a repeating event, returning none of its content — so unlike `delete_contact`, there is no `deletedCard`-style copy in the response to rebuild from. The confirmation names the deleted event by its own UID, as `update_calendar_event`'s does, even when you passed its `url`, and gives the url of the resource actually deleted, since a UID can spell another event's url. Call `get_calendar_event` first when the id might be wrong: that response is the only copy you will have, and it is also how you see whether anyone is about to be mailed.

### Identity & Testing Tools

- **list_identities**: List sending identities (email addresses that can be used for sending). Returns simplified format by default, including the identity's configured `textSignature`/`htmlSignature` when it has one (see [Identity fields](email.md#identity-fields) for how to use them, and [Signing a message](email.md#signing-a-message) for the `{{signature}}` token that writes them into a body for you). **An identity's `email` may be a wildcard pattern** (`*@example.com`) rather than an address: it verifies and signs any concrete address in that domain, but the pattern itself cannot be used as a `from` value — pass a concrete address in its domain instead. See [Wildcard identities are not addresses](#email-tools).
  - Parameters: `verbose` (optional, include all fields), `raw` (optional, return original JMAP response)
- **check_function_availability**: Check which functions are available based on account permissions (includes setup guidance). Calendar tools run over CalDAV, so calendar is reported available only when CalDAV credentials are configured, regardless of the JMAP calendar capability. Contacts is reported available only when the session carries both the JMAP contacts capability and a primary account for it. That confirms **read** access only: a read-only contacts token reports exactly the same capability, so `create_contact`/`update_contact`/`delete_contact` are listed as available and only refuse when a write is attempted.
- **test_bulk_operations**: Test `bulk_mark_read` on up to 10 recent Inbox messages. The default dry run writes nothing and lists the messages with their current read state (`wasRead`). With `dryRun: false` it **writes to those real messages**: it marks them all read, then marks unread again only the ones that were unread before, so each ends in its own prior state; a message whose read state was not reported is left out of both steps and listed with `excluded: true` instead of `wasRead`. If that second step fails, messages that were unread can be left read; the result reports each step.
  - Parameters: `dryRun` (default: true), `limit` (default: 3, max: 10)

## Experimental: snooze

Fastmail refuses snooze to API tokens: the capability that carries it answers "Disallowed capabilities for this type/client", and Fastmail's help says third-party clients cannot snooze. Its own web client can, so these tools run on that client's login instead of your API token. They are off unless you set `FASTMAIL_EXPERIMENTAL_SNOOZE=1`, and they are not in the tool count above. The measurements behind them are on [#35](https://github.com/JonathanGodley/fastmail-mcp/issues/35).

**Without them, the API token still shows which messages are snoozed, but not until when.** A snoozed message carries `snoozed` in its `roles` on every read tool, and `list_emails` with `mailbox: "Snoozed"` lists them all. The wake time is the part Fastmail withholds: asked for with an API token, it is refused as an invalid argument, and sorting by it as an unsupported sort.

**What you are handing over.** `FASTMAIL_WEB_COOKIE` is the session cookie of a logged-in Fastmail web login. It carries everything that login can do, not a scoped permission, and anyone holding it is logged in as you. It stops working when that login ends, for example when you log out of that browser or Fastmail ends the session; the tools then say so. Keep it in `~/.fastmail-mcp/.env` like the API token.

**Getting the cookie.** Log in to Fastmail in a browser and open its developer tools on the Network tab. Click any request to `api.fastmail.com` and copy, from its request `Cookie` header, the one pair whose name starts `__Http-s_`. Set it with the name and value, in quotes:

```bash
FASTMAIL_EXPERIMENTAL_SNOOZE=1
FASTMAIL_WEB_COOKIE="__Http-s_xxxxxxxx=<value>"
```

The server exchanges the cookie for the web client's bearer token itself, as the web client does, and fetches a new one when it is refused.

- **list_snoozed_emails**: List the messages in the Snoozed mailbox, soonest wake time first. Returns `{ total, emails }`; `total` is omitted when Fastmail does not return it, and then a full page may not be every snoozed message. Each email is the [simplified shape](responses.md#response-simplification) `list_emails` returns, plus `wakeAt` (local time with a UTC offset, like `date`) and `wakeInto`, the mailbox it returns to, normally the Inbox. As on `list_emails`, `sentAt` is left out. With `raw: true` the emails are the JMAP objects as fetched, `sentAt` included, whose `snoozed` property carries the wake time in UTC.
  - Parameters: `limit` (default: 50, max: 100), `raw` (default: false)
- **snooze_email**: Snooze an Inbox message until a time. It leaves the Inbox for Snoozed, keeping its other labels, and at that time Fastmail returns it to the Inbox marked unread, which is what the Fastmail app writes. On a message already snoozed it changes the wake time only. A message outside the Inbox is refused. Returns `{ emailId, wakeAt, wakeInto }`, plus `previousWakeAt` on a message that was already in Snoozed (null when it had no wake time); `wakeAt` and `previousWakeAt` are local time with a UTC offset.
  - Parameters: `emailId` (required), `until` (required: a datetime in the future; one with no offset is local time in `FASTMAIL_TIMEZONE` or the host's zone, as for `search_emails`' `after`)
- **unsnooze_email**: Return a snoozed message to the Inbox now and clear its snooze. Its read state is left as it is. Returns `{ emailId, movedTo, wasWakeAt }`, `wasWakeAt` in local time with a UTC offset.
  - Parameters: `emailId` (required)

Moving a message out of Snoozed with `move_email` also clears its snooze: Fastmail drops the wake time itself when the message leaves Snoozed.
